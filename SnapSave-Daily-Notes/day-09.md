### 1. Objective

The main goal of Day 9 was to connect the existing SnapSave financial intelligence pipeline with a real AI provider.

## 2. Why Gemini Was Added

The existing AI prompt system from Day 8 was only preparing the information required by an AI model.

It did not yet communicate with a real AI service.

For Day 9, Gemini was selected as the AI provider.

The official Google Gemini SDK was added to the backend:

`@google/genai`

This gives SnapSave a provider layer instead of placing AI API calls directly inside controllers.

This separation is useful because the rest of the application does not need to know the internal details of the Gemini API.

## 3. Gemini Provider

A new provider file was created:

`backend/src/services/ai/geminiProvider.js`

The provider is responsible for communicating with Gemini.

Its main responsibilities are:

- Read the Gemini API key from environment variables
- Create the Gemini client
- Send the financial prompt to Gemini
- Request JSON output
- Handle temporary API failures
- Return the generated response

The API key is stored in `.env` and is not committed to GitHub.

The `.env` file is already ignored by Git.

## 4. Lazy Gemini Client Initialization

During testing, an API-key warning appeared when the Gemini provider was imported.

The reason was that the Gemini client was being created immediately when the file was loaded.

This meant even tests that did not call Gemini were initializing the Gemini SDK.

The provider was changed to use lazy initialization.

Now the Gemini client is created only when:

`generateRecommendation()`

actually needs to make an API request.

This gives two advantages:

1. Unit tests that only test parsing and validation do not initialize Gemini.
2. The application only creates the external AI client when it is actually required.

After this change, the API-key warning disappeared from the Jest tests.

## 5. Gemini Model

The provider was configured to use:

`gemini-3.8-flash`

An earlier model configuration was tested, but the API indicated that the model was no longer available for new users.

The provider was therefore updated to the available model returned by the API.

The Gemini API was also tested during development.

The configured model returned a temporary `503 UNAVAILABLE` / high-demand response during testing.

Because temporary availability problems can happen with external AI services, retry handling was added.

---

## 6. Retry Handling

The Gemini provider checks for temporary failures such as:

- `503`
- `UNAVAILABLE`
- high-demand responses

When one of these temporary errors occurs, the provider retries the request.

The retry delay increases between attempts.

The current implementation uses exponential backoff:

- First retry: 1 second
- Second retry: 2 seconds

The maximum retry count is configurable through the function options and defaults to 2 retries.

Permanent errors are not repeatedly retried.

This prevents the application from continuously calling the API when the problem is not temporary.

---

## 7. AI Recommendation Service

A second service was created:

`backend/src/services/aiRecommendationService.js`

This service sits between the existing financial context/prompt system and the Gemini provider.

Its job is to:

1. Build the existing financial prompt
2. Send the prompt to Gemini
3. Receive the AI response
4. Parse the response as JSON
5. Validate every recommendation
6. Return only properly structured recommendations

This keeps AI response processing separate from the Gemini API implementation.

---

## 8. Structured Recommendation Format

SnapSave does not simply accept any text generated by the AI.

Every recommendation is expected to contain five fields:

- `type`
- `title`
- `message`
- `evidence`
- `action`

Example concept:

**Type:** SPENDING_INCREASE

**Title:** Food spending increased

**Message:** Food spending increased compared with the previous period.

**Evidence:** Spending increased by a measurable amount.

**Action:** Review recent food expenses.

The important part is that the recommendation contains both an observation and supporting evidence.

This follows the design decision from Day 8 that the AI should work from supplied financial context rather than inventing financial facts.

---

## 9. Recommendation Validation

A validation function was added:

`validateRecommendation()`

It checks that:

- The recommendation is an object
- It is not an array
- All required fields exist
- Every required field is a non-empty string

If any required field is missing or invalid, the recommendation is rejected.

This creates a safety layer between the external AI response and the rest of the SnapSave application.

---

## 10. AI JSON Response Parsing

The Gemini provider is requested to return JSON.

The recommendation service therefore expects the response to be a JSON array.

The parser checks three important conditions:

### Valid JSON

If the AI returns invalid JSON, the service rejects it.

### JSON array

The response must be an array of recommendations.

A single object is not accepted as the final recommendation structure.

### Valid recommendation objects

Every item inside the array must contain all five required fields.

If even one recommendation object is invalid, the response is rejected instead of silently passing incomplete AI output to the application.
